Results, storage, and replay

The checker hands results to another set of workers. It does not write each check directly to PostgreSQL. This separates network checking from batched storage, but it also creates a period where a completed check is not yet durable or visible to API readers.

There are several success boundaries​

AddProxyStatisticForWorkspaces returns no admission or commit status to its caller. The checker can finish and schedule another cycle before this result appears in PostgreSQL. Queue completion is separate from result persistence.

Admission can wait, fall back, or drop​

Redis Streams are enabled by default. Producers append to magpie:proxy_statistics:stream; consumers share a group and buffer results. The normal flush threshold is 5,000 results or a 15-second timer per worker. Recovered partial pending batches also flush before waiting for new traffic.

A flush can contain several transactions. Each transaction normally covers at most 5,000 potential latest-evidence rows, counting valid workspace evidence and at least one row per physical result. Eight workspaces sharing each result therefore produce transactions of at most 625 results. A single result with more evidence than the limit stays together in one transaction. Preparation and all transactions in one flush share the same 30-second deadline.

When Redis is disabled, stream initialization is incomplete, or stream admission fails, results can enter a memory fallback queue. Initialization retries after an outage. Memory fallback is volatile and has no replay identity.

Overload policyBehavior to understand
block, the defaultWait/retry with a default 500 ms producer budget. Redis operation timeouts and retry sleeps mean this is not an exact wall-clock deadline.
drop_newReject a new result when admission is full. An intentional stream rejection bypasses memory fallback.
evict_oldestApproximate stream trimming can discard unread or pending results. The memory path uses a timed wait instead of eviction.

The memory queue defaults to 20,000 entries. Stream capacity checks and appends are separate operations, so concurrent producers can exceed the nominal cap. Rejected results are counted and logged; the checker receives no error from this void handoff.

PROXY_STATISTICS_TENANT_OVERLOAD_POLICIES retains a legacy name and uses workspace IDs. A shared result chooses the strongest policy among the default and applicable overrides: block, then drop_new, then evict_oldest. Overrides cannot weaken the default. A nonpositive producer-block timeout allows unlimited stream retries under block while providing no memory wait. See the environment reference before changing admission settings.

What commits together​

InsertProxyStatistics commits accepted data in one PostgreSQL transaction:

  • Replay-event identities, so the same stream event is not inserted twice.
  • Physical check history with workspace evidence.
  • Check counters and workspace usage attributed through the existing batch.
  • Latest evidence keyed by workspace, configuration, route, and protocol.
  • Durable requests to refresh affected reputation data.

Latest-evidence writes take conflicting rows in a consistent order. The transaction writes latest evidence and reputation requests before updating shared usage rows, so imports do not wait on usage while the larger evidence set is written. Any legacy overall-status aggregation follows those writes, preserving its serialization through shared reputation or usage rows. Usage still commits atomically with the result and replay identity.

A delayed older event cannot replace newer latest evidence. Obsolete settings can contribute historical evidence without defining current health. Before inserting, consumers exclude routes that have been deleted. Malformed stream entries are logged and discarded with acknowledgement/deletion. A successful flush therefore does not mean every originally submitted item became history.

Replay handles an uncertain acknowledgement​

Failure pointRecovery
A transaction fails before commitKeep its original results and the remaining suffix for retry. Earlier committed prefixes remain handled; their stream IDs can be acknowledged.
Commit succeeds, then acknowledgement failsRetry acknowledgement; another worker may reclaim idle pending entries. Event identities prevent duplicate history and counters.
Consumer crashes with a pending stream batchAnother consumer can reclaim surviving entries and retry.
Redis loses an entry before PostgreSQL commitQueue reconstruction cannot recreate that result. Redis persistence and overload policy matter.
Shutdown has memory-only resultsWorkers retry the remaining buffer in bounded flushes. Unfinished draining makes the background shutdown deadline fail; a forced exit can still lose those volatile results.

Memory consumers remove each committed original prefix before retrying a failed suffix. Stream consumers match acknowledgements to original event IDs, including discarded malformed or deleted-route entries. Filtering or replay deduplication cannot shift that correspondence and acknowledge an uncommitted result.

Replay protection is part of the same transaction as history and counters. Stream maintenance retires old event identities behind a durable replay floor while preserving protection for unread and pending entries. Coordinated PostgreSQL and Redis backups preserve those relationships.

Read models refresh after the durable result​

Reputation, source counts, filters, and dashboard caches can lag history. They are derived views, rather than another copy of an individual check's durability guarantee. Health reads also verify the current checker generation, so a stale settings projection cannot make old evidence current.

Proxy-list projection batches read evidence for their dirty workspace/route pairs and reuse that bounded evidence for current health and latest-check fields. Shared ownership does not require scanning every workspace's inventory. Concurrent projection writers lock rows in workspace/route order. Background batches have a 30-second default deadline and retain failed or timed-out work. A projection-prefix child deadline can reduce that failed interval's next statement to half its previous width while its parent refresh context remains active. Each successful subprefix advances the contiguous committed cursor; the ordinary width returns after that interval finishes. There is no retry inside the failed invocation. This can increase exceptional database round trips. Parent cancellation, permanent errors, and unresolved one-pair work cannot be skipped. Owner discovery shares the first prefix's child deadline. Discovery and the final source lookup do not create or split a projection retry interval. A normal pass still handles at most four projection statements. READ_MODEL_REFRESH_TIMEOUT_SECONDS changes that batch deadline; it does not extend the overall shutdown allowance or the time allowed for a proxy check. During final shutdown, proxy and source batches retry with a 250 ms backoff until both dirty queues are empty. Source-counter batches keep their separate 30-second deadline. If draining cannot finish within BACKGROUND_SHUTDOWN_TIMEOUT_SECONDS, shutdown reports an error.

Startup reconciles projection indexes created under older names. It removes known redundant copies only when an equivalent valid index remains, and keeps indexes with different definitions or clustering settings. Large installations may spend additional startup time building page/filter indexes. Wait for readiness before sending traffic, and include this migration work in upgrade and recovery timing.

Retention keeps storage bounded. Detailed history and response bodies have separate retention settings. Monthly partitions are prepared ahead of time, and older daily counters compact into lifetime totals. Obsolete latest-evidence cleanup uses bounded key-ordered pages and resumes unfinished scans on later maintenance passes. It preserves dirty workspace namespaces and matching legacy, default, and tag-override evidence, so referenced current checks remain pinned in history. Successful checks skip already-zero failure streak updates, x^failed checks skip streaks already at 255, and metadata enrichment skips rows whose country and type are unchanged. The storage reference describes table responsibilities; backup and recovery covers restoration.

Checkpoint: PostgreSQL committed a result and the worker crashed before acknowledging Redis. Will replay double the check count?

For the identified stream event, the transaction's replay ledger prevents a second history insert and counter increment. The event can be handled again and acknowledged. Memory fallback has no equivalent restart replay path.
