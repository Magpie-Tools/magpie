Code map and reading exercises

Use this page after reading the workflow chapters. You do not need to read every backend file. Pick a behavior, find its entry point, and read the tests that describe its edge cases.

Exercise 1: trace a single upload​

Find addProxies and ingestProxyUploadMultipartWithTags in the upload handler. Follow a flush into InsertAndGetProxiesWithWorkspace. Identify the transaction that stores routes and management, then locate tag assignment and Redis publication after it.

Explain which changes can remain committed if the response reports a later failure. Read route_proxy_handler_test.go and proxy_access_storage_test.go for explicit workspace selection and exact credential identity.

Exercise 2: explain the queue cost​

Follow GetNextProxyContext, RequeueProxy, and RequeueProxyWithPayload. Compare pop.lua and complete.lua. Find these regression tests:

  • TestQueuedProxyToDomainProxy_CurrentPlaintextPayloadReusesHashWithoutEncryptionKey in proxy_queue_test.go.
  • TestRequeueProxy_OnlyPersistsPayloadWhenRequested in the same file.
  • TestPlaintextProxyCycleCommandBudgetAndPayload in proxy_queue_concurrency_test.go.

Explain why normal completion cannot overwrite a newer payload. Count cipher operations, JSON encodes, Redis client calls and internal commands, and database queries before proposing any hot-loop change. A new operation needs representative throughput measurements and a written reason.

Exercise 3: follow conflicting workspace verdicts​

Read buildRequestAssignments, processJudgeAssignments, and CheckProxyWithRetries in the checker. Then read TestSharedRequestKeepsWorkspaceValidationEvidence in tag_settings_test.go. Trace the evidence through InsertProxyStatistics to latest health reads.

Explain why one physical response can produce opposite workspace health and why a changed configuration cannot reuse every old success.

Exercise 4: crash between commit and acknowledgement​

Read proxy_statistics_recovery_test.go, proxy_statistics_shutdown_test.go, and proxy_statistics_idempotency_test.go. Locate the event ledger write inside the statistics transaction.

Explain what another consumer can replay, what prevents duplicate counters, and why the memory fallback has a weaker recovery guarantee.

Validate changes in the right environment​

The local development guide sets up PostgreSQL and Redis. Use disposable test services and separate Redis databases for queue concurrency tests; those fixtures flush their selected test database. Do not point them at a running instance's Redis.

For a queue or checker change, run the required backend checks from magpie-backend:

go test ./... -count=1
go test -race ./... -count=1
go vet ./...
go build ./cmd/magpie

Real-service tests use MAGPIE_TEST_POSTGRES_DSN, MAGPIE_TEST_REDIS_URL, and MAGPIE_TEST_QUEUE_REDIS_URL for their respective fixtures. Many tests use SQLite or miniredis without those settings, while tests requiring real services skip. Passing a skipped test does not measure PostgreSQL query cost or production Redis concurrency. See testing and performance validation.
